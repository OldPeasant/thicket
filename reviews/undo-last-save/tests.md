## Bugs found

### Undo of a save that removed several trailing fields restores them in the wrong order

Finding ID:

`TW-2`

Test:

`test/e2e/undo-last-save.e2e.ts` > `Undo last save of the last two fields restores them in their original order`

Production source:

`packages/renderer/src/app/document/history/apply-update.ts:10-44` (`applyUpdate` appends new fields in the order of the ops), used by `keepingOrder` in `packages/renderer/src/app/document/document-actions.service.ts:699`

Requirement:

AC1 ("server doc equals original"), and the task assumption that the undo of a whole, non-projected document is sent as replaceOne "when the minimal update would leave fields in another order (MongoDB appends a re-added field)".

Expected behavior:

Seed `{_id: 1, status, addr, placed, ref, tags, total: Decimal128, qty: Int32}`, delete `total` and `qty` in the UI, save, then Undo last save. The stored document has the original field order again, with `total` before `qty`.

Actual behavior:

The message is "Undid the last save of 1.", but MongoDB stores `..., "tags":[...], "qty":1, "total":10.50`, so `qty` now comes before `total`. `keepingOrder` predicts the result of the undo's `$set {total, qty}` with `applyUpdate`, which appends new fields in op order (`total`, `qty`). That prediction equals the original, so the minimal update is sent. MongoDB 5.0+ (the fixture is 8.x) applies update operator fields in lexicographic field-name order, so it appends `qty` first. The test shows this directly: the driver read-back has `qty` before `total`.

Severity:

Medium (no data is lost, but the restored document is not equal to the original in field order, which the task promises).

Fix required:

`Yes — production code must be fixed by the parent worker / fixer.`

### Undo of a save that added several sub-fields to an embedded document is refused as a false conflict

Finding ID:

`TW-3`

Test:

`test/e2e/undo-last-save.e2e.ts` > `Undo last save of two sub-fields added to an embedded document restores the original`

Production source:

`packages/renderer/src/app/document/document-actions.service.ts`: `undoSave` (around line 180) sends with `last.after` (the document as the client sent it, `recordSave` at around line 150) as the conflict-check base. `savedVersion`/`applyUpdate` (`document-actions.service.ts` around line 722, `history/apply-update.ts`) model new sub-fields in op order on the replace path.

Requirement:

AC1 (save, undo last save -> server doc equals original). AC2 only allows a conflict when "the document changed on the server since".

Expected behavior:

Seed `addr: {city: "Springfield"}`. In the UI add the keys `zip` and then `apt` to `addr` (2 changes), save, then Undo last save. Nothing changed on the server since, so the undo succeeds and the stored document equals the original.

Actual behavior:

"Not undone: the document was changed on the server since the save. Nothing was overwritten; ...". The undo is then dropped and can't be retried. The save's `$set {"addr.zip": "", "addr.apt": ""}` is applied by MongoDB in field-name order, so the server stores `addr: {city, apt, zip}`. The undo's check is `addr: {$eq: {city, zip, apt}}` (from `last.after`). `$eq` on an embedded document is order-sensitive, so it never matches. On the replace path, `savedVersion` (`applyUpdate`) would predict the same wrong order. Nothing is overwritten, so the failure is safe. But nothing changed on the server, so the message is false and AC1 fails for this kind of save. The cause is related to TW-2 (MongoDB's lexicographic update order is not modelled), plus the undo's minimal-path check uses the sent document, not the stored one.

Severity:

Medium (a safe failure: nothing is overwritten. But undo silently becomes unusable after an ordinary edit and reports a conflict that did not happen.)

Fix required:

`Yes — production code must be fixed by the parent worker / fixer.`

(For the fixer to decide, not a prescription: model MongoDB's update order in `applyUpdate`, so new fields at one level are appended in lexicographic order and numeric names in numeric order. Or base the undo's `after` and its conflict check on the document as read back from the server after the save, for non-partial documents. The first test asserts only the set of `addr` keys, not their order, so it doesn't depend on which fix is chosen.)

Notes, not findings:
- Save itself may share the TW-3 behavior for a second edit to the same embedded document right after such a save, because the edit session is rebased onto the sent document. That is outside this task's changed behavior and was not tested.
- The fixer's known limitation was confirmed by reading the code, not by a test: query `$eq` is numeric-type-insensitive (Int32 7 matches Double 7) and traverses arrays. So a server-side numeric type change of an otherwise equal value is not a conflict. Save's existing check has the same limitation.
